# v1.2.0 hosted acceptance

How the v1.2.0 release candidate is accepted against a temporary
temporary release-candidate deployment, and what would make it fail.

**This is deployment acceptance, not a research-quality evaluation.**
One run says whether the pipeline works end to end under the public
budgets. It says nothing about whether the engine answers questions
well, and a single good answer would not be evidence that it does.

Production stays on v1.1.1 throughout. Nothing here touches it.

---

## What v1.2.0 adds, and therefore what has to be observable

Four decisions that did not exist in v1.1.1:

| Decision | Where it is recorded |
| --- | --- |
| The answer contract the question was decomposed into | `contract.json` |
| Proposition decomposition and per-part entailment | `propositions.json` |
| Relevance, structural and judged, separately | `relevance-decisions.json` |
| Bounded wording repair, accepted **and refused** | `repairs.json` |

None of these were in the SSE payload before this release, and the
service runs with `PERSIST_RUNS=false`. If a decision is not in the
stream it does not exist once the run ends — which is how the first
hosted capture lost its own result payload to a 150-character
truncation. Acceptance is therefore as much about what survives the
run as about what the run decided.

## The candidate deployment

`deploy/render-rc.yaml`. Temporary, deleted after acceptance.

| | |
| --- | --- |
| Service | `agentic-research-engine-rc` |
| Branch | `feat/v1.2.0-research-quality`, pinned |
| Auto-deploy | off — a push must not replace the build mid-acceptance |
| Custom domain | none |
| Live research | **`false` at first deploy** |
| Daily admissions | **1** = 30 // 30 |
| Run shape | 1 round, 6 sources, 240s — identical to production |
| Quota store | **shared with production** |
| Quota namespace | `rc` |
| NLI endpoint | **shared with production**, same pinned revision |

Render permits one free Key Value instance per workspace and
production has it, so the candidate connects to the demo's store. A
second instance is a paid resource for a deployment that exists to be
deleted.

That makes `DEMO_QUOTA_NAMESPACE` load-bearing rather than defence in
depth: it is the only thing keeping the two counters apart. Both
deployments INCR against one store, and without a namespace they
compute the same daily key — a candidate run would silently spend one
of production's five, with nothing to show for it but a short
allowance. The namespace sits between the fixed prefix and the UTC
date; since the date is always last and a namespace may not contain
the key separator, no namespace can spell production's key.

The blueprint tests assert the value is present, different from
production's, and accepted by the real validator, and a further test
runs both blueprints' actual namespace values against one shared
store to confirm neither eats the other's allowance.

### What this costs while it exists

The caps compose by addition, not by maximum.

| | Public demo | Candidate | Worst case while both exist |
| --- | --- | --- | --- |
| Runs/day | 5 | 1 | 6 |
| OpenAI $/day at the $0.05 per-run ceiling | $0.25 | $0.05 | $0.30 |
| Tavily credits/day | 40 | 8 | 48 |

Hugging Face is billed per warm hour, not per run, and the endpoint is
shared. A candidate run wakes it and starts an hour exactly as a
production run would — charged whether or not the run succeeds. This
is the cost of accepting a release, and it is the reason the service is deleted rather
than left running.

The $5 OpenAI project limit does not bound Hugging Face or Tavily.
Those are three separate cost domains with three separate limits, and
none of them bounds the others.

## The procedure

### 1 — Deploy the candidate with live research off

Create the Blueprint from `deploy/render-rc.yaml`. Paste the
same credentials production uses at the prompts, plus the production
Key Value instance's **internal** connection string for
`DEMO_QUOTA_URL`. Leave `LIVE_RESEARCH_ENABLED` at `false`.

The internal URL, not the external one: the instance has
`ipAllowList: []`, so an external URL will not connect and readiness
will fail closed rather than admitting runs uncounted.

All seven prompted values are required even with live research off:
`LLM_MODE=cloud` is validated at startup, so a missing
`OPENAI_API_KEY` refuses the boot rather than deferring the failure to
the first request. That is deliberate — it means enabling live
research afterwards is a single environment flip with nothing else to
change, and therefore nothing else that can be got wrong at the moment
money starts being spent.

The interlock matters: the service boots, serves replay, and answers
readiness without ever reaching a paid provider, so an unreviewed
branch cannot spend money before anyone has looked at it.

### 2 — Credential-free checks

```
python examples/live-validation/tools/acceptance.py checks \
  --base https://agentic-research-engine-rc.onrender.com
```

Spends nothing and needs no credentials. It probes health, readiness,
config, every recorded example, and confirms the interactive schema is
not served. It then POSTs to the research route — but **only after
readiness reports live research disabled** — because that is the only
way to show the interlock holds in the process rather than in the
blueprint.

All checks must pass before anything else happens. The research probe
reports `SKIP`, not `FAIL`, when live research is enabled — run
against production it prints `15/15 passed, 1 skipped` and exits 0,
which is what makes a non-zero exit worth reacting to.

### 3 — Preflight

Not run yet. Preflight retrieves the configured model from the OpenAI
project and verifies the NLI endpoint's pinned revision against the
Hugging Face control plane. Both are non-generating but both are
authenticated calls to a paid account, so they wait for authorisation
along with the run.

### 4 — Exposure, stated before spending anything

Before the run, write down what the worst case is: one admitted run,
at most `MAX_PROVIDER_REQUESTS` (30) provider requests, `MAX_CLOUD_COST_USD`
($0.05) reserved, at most `MAX_SEARCH_CREDITS` (8) Tavily credits, and
one Hugging Face warm hour. If the run overruns any of these, the
reservation was wrong and that is itself a finding.

### 5 — One authorised run

Enable `LIVE_RESEARCH_ENABLED=true` in the Render dashboard. Then:

```
python examples/live-validation/tools/acceptance.py capture \
  --base https://agentic-research-engine-rc.onrender.com \
  --question "How does a large language model differ from a neural network?" \
  --out examples/live-validation/v12-<timestamp>
```

Bytes go to disk as they arrive and are flushed per chunk, so a
process killed mid-run still leaves everything that reached it. Timing
goes into a separate index; the stream file is never annotated.

The daily cap is 1. There is no second attempt without a further
authorisation, so nothing about the derivation may depend on rerunning.

### 6 — Derive the artifact, offline

```
python examples/live-validation/tools/acceptance.py build \
  --run-dir examples/live-validation/v12-<timestamp>
```

Reads the captured bytes and writes the report, metrics with their
derived reconciliation, the contract, the propositions, the relevance
decisions, the repairs, the citations, the provider usage, and the
non-result event log. Every file is scanned against the forbidden
patterns before it is written: a refusal at build time is recoverable,
a credential in a commit is not.

`README.md`, `manual-review.md` and `environment.json` are written by
hand afterwards, then `build` is re-run so the checksums cover them.

### 7 — Manual review

Read the report against its own citations. The engine cannot tell you
whether a supported, relevant, well-cited claim is a *good* answer.

## Acceptance criteria

The candidate passes only if all of these hold. Any one failing is a
finding to fix, not a number to restate.

**The run completed**

- [ ] The capture contains `event: result` and `event: done`
- [ ] Wall clock within `DEMO_MAX_RUNTIME_SECONDS` (240s)
- [ ] Provider requests ≤ 30, cost ≤ the reserved bound

**v1.2.0's decisions are observable**

- [ ] `contract.json` is non-null and carries required slots
- [ ] Any claim asserting more than one thing has its parts in
      `propositions.json`, each with its own entailment score
- [ ] Every claim that reached the relevance gate appears in
      `relevance-decisions.json` with a stage of `structural` or `judged`
- [ ] Any repair appears in `repairs.json` with **both** wordings, and
      every refused repair is there too

**The gates did their job**

- [ ] No published claim cites an evidence id that does not resolve
- [ ] Every published claim's quote appears in its source
- [ ] No repair added a number, a named subject, a causal link, or
      strengthened a modality — check `repairs.json` by hand
- [ ] A published claim answers the question, judged by reading it

**Nothing leaked, nothing else changed**

- [ ] No credential, endpoint URL or local path in the artifact
- [ ] Production still reports `1.1.1` at `/api/health`
- [ ] Production's readiness is unchanged

A zero-publication run is **not** automatically a failure. It is a
failure if the reason is a defect; it is a correct result if the
evidence genuinely did not support the claims. The artifact has to say
which, and say it in `manual-review.md` rather than leaving a reader
to infer it from a count.

---

## Teardown

Delete the candidate web service. **Not** the Key Value instance — that
one is production's, and the candidate was only borrowing a namespace in it.

A candidate deployment left running is a second thing holding
credentials and a second thing that can wake the paid endpoint.

The `are:live-runs:rc:<date>` keys expire on their own 36-hour
TTL, so nothing has to be cleaned out of the store by hand.
